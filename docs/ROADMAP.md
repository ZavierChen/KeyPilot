# 发展方向与前景

[项目首页](../README.md) · [当前功能](PROJECT_OVERVIEW.md) · [亮点与同类方案](DIFFERENTIATION.md) · [版本历史](VERSION_HISTORY.md)

更新日期：2026-09-18。本页记录作者的产品目标、工程路线和商业设想；规划中的功能、成本目标及合作方向不作为当前已交付的能力。

## 愿景：Siri 式交互，AI 代理执行

KeyPilot 从“替代 Copilot 键，再做一个 Windows 版 Siri”出发，长期目标是让不同品牌、小厂整机和自配 Windows 电脑，都能以较低成本获得接近系统原生的助手体验：随手唤起、直接说出需求、操作电脑，并用自己选择的声音回复。

这个目标源于作者电脑上 Copilot 键只打开搜索的实际经历。后续截图确认该键当前绑定为“搜索”，也提供“打开应用”选项；作者没有实际用过 Copilot。项目关注的是怎样把这个物理入口做成能直接帮用户完成操作的助手体验。

**交互体验的参照是 Siri，执行能力的发展目标是 AI 代理：随手唤起、自然表达需求，由助手完成任务并反馈结果。** 常用操作直接执行，复杂目标逐步扩展为“规划 → 操作 → 检查 → 反馈”的任务流程。模型选择、英文版、声音定制与部署改进，都服务于这个完整的个人助手体验。

近期重点是把已有工程变成普通用户能够安装和持续使用的成熟 App。用户应当能够在应用里选择本地模型、API 模型和声音，而不必先学会搭建开发环境。基础操作保持免费使用；本地推理与本地合成降低持续服务费用，需要更强能力时再由用户选择云端服务。

成本路线也包括利用可选服务的免费额度。现有 Marvis 转接就源于作者使用时的每日免费 Token：在额度内补充云端代理能力，付费 API 留给确有需求的用户。产品化时应清楚显示服务和额度来源，具体条件见[选择 Marvis 的原因](PROJECT_OVERVIEW.md#为什么选择-marvis)。

“给每台电脑提供类似 Siri 的功能”是长期愿景。当前实现聚焦 Windows 的已注册操作；不同硬件、系统版本和模型能力仍需分别适配、验证。

## 现有基础与下一步目标

| 方向 | 当前已有基础 | 下一步要达到的体验 |
| --- | --- | --- |
| 安装与部署 | 固定依赖、安装脚本、统一启动、环境检查与源码发布包 | 安装 App 即可使用基础功能，无需手动配置 Python、命令行或运行环境 |
| 本地模型 | Ollama / OpenAI 兼容服务接入、模型发现、响应校验与只读探测 | 自动识别硬件，选择适合的模型，一键下载、校验、启动与切换 |
| API 模型 | 兼容 API 地址、密钥保存、连接测试与模型选择 | 在向导中选择服务商、完成必要授权，再选择模型；展示连接状态与费用来源 |
| AI 任务执行 | 已注册 Skill 的单次执行与反馈；有限 Codex 回传；ChatGPT/Marvis 需求投递 | 多步骤计划、可见进度、结果检查、失败恢复；外部代理完成状态返回同一界面 |
| 英文版与语言切换 | 当前界面、常用规则和多处提示以中文为主；语音已有中英分流及英文实验记录 | 提供英文界面、英文命令和问答、英文听写与朗读，并验证英文 Windows 环境，保留中英切换 |
| 个性化声音 | 本地包规范、资源与加载校验、导入试听；已有多条语音实验路线 | 短样本录音向导、质量检查、可选制作方案和自动导入 |
| 持续使用 | 按需加载、预热、可中断朗读、配置持久化和历史修复 | 完整升级、回滚、恢复、卸载和错误诊断，跨机器使用不再依赖开发者协助 |

“零配置环境”指用户无需手动配置运行环境。模型文件仍需下载，麦克风仍需授权，使用付费 API 时仍需账户或密钥；应用负责把这些步骤做成清楚、可恢复的引导。

## 近期路线：先成为成熟 App

| 阶段 | 主要工作 | 完成标准 |
| --- | --- | --- |
| 1. 安装后就能完成基础操作 | 应用安装包、运行环境管理、首次启动向导；麦克风与按键选择；评估签名 MSIX 和系统按键注册；统一管理按键与计时后台、退出和卸载 | 在未安装开发环境的干净 Windows 电脑上，通过界面完成安装、启动、文字操作、计时任务与基础朗读；异常可诊断，卸载能区分程序和个人数据 |
| 2. 在应用里选模型 | 硬件与磁盘检查、经过验证的模型目录、下载进度与恢复、模型切换、API 服务向导 | 普通用户无需打开终端即可接入一款已支持的本地模型或 API 模型；下载、鉴权或加载失败时仍保留基础操作 |
| 3. 打通有限多步骤任务 | 从现有 Skill 组合任务，显示步骤与进度，检查结果，接回外部代理状态 | 固定任务集可验证实际完成；“已发送”“执行中”“已完成”明确区分；失败能停止，用户可以取消或接管 |
| 4. 完成声音定制闭环 | 短样本采集、噪声和转写检查、本地 GPU 与云端辅助制作选项、训练进度、试听及包导入 | 从参考录音到可用声音均有明确状态；独立测试文本可正常发声，失败可重试且不覆盖已有可用音色 |
| 5. 验证日常使用质量 | 更新与回滚、不同硬件适配、长期运行和冷启动检查、有限范围的离线识别评估 | 记录安装成功率、操作成功率、首音等待、空闲资源和付费调用量；用真实使用反馈决定后续扩大范围 |

本地模型目录应优先提供少量经过验证的组合，并说明下载体积、硬件需求、操作契约通过情况和模型许可。兼容同一种 API 不代表所有模型都有相同的理解或执行质量。

近期先打通“安装 → 选择模型 → 完成常用操作”的路径，再把声音制作和硬件合作纳入稳定产品。具体发布时间以这些验证结果为依据。

微软已有第三方应用的 Copilot 键注册规范：应用需要符合打包和签名要求，并在清单中声明 `com.microsoft.windows.copilotkeyprovider`。因此可评估将正式安装版 KeyPilot 接入 Windows 的“打开应用”选择器，让用户直接指定按键目标。当前源码启动器与可选按键监听并不等于已经完成此注册。[官方开发者规范](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/microsoft-copilot-key-provider)

### 近期并行目标：从单次操作发展到任务代理

已有的“输入 → Skill → 执行 → 反馈”是基础；下一步让用户交代一个目标，再由助手组织具体步骤。例如“打开学习资料和课程网站，再设一个 25 分钟计时器”，可以先用已有操作验证任务编排，再逐步增加文件处理与跨应用工作流。

1. **计划与执行分开。** 模型提出有限步骤，由执行层校验操作和参数；先支持已注册 Skill 的组合，再扩大工具范围。
2. **让任务进度可见。** 显示当前步骤与实际反馈，提供取消和接管；涉及覆盖文件、发送内容等动作时按风险设计确认。
3. **检查真正的结果。** 为各类动作定义可观察的完成条件，失败时停止或进行有次数上限的重试；单纯发送请求不标记为完成。
4. **统一外部代理回传。** 为可集成的服务定义任务 ID、进度、结果和错误接口；将返回内容接入界面和语音反馈。只有支持结果回传的适配器才显示完整任务状态。

当前 Codex 桥接只接收限定结构的短答或设置请求，ChatGPT/Marvis 主要完成需求投递；它们尚未组成通用代理执行循环。规划中的第一阶段以小范围、可验证的任务为验收对象，记录完成率、错误恢复、取消有效性、耗时和付费调用量。项目长期目标是扩展实际完成任务的范围，同时保留基础操作无需云端推理费用的路径。

### 近期并行目标：英文版与中英切换

英文版是近期明确目标，与安装和模型选择一起推进。目标是让英文用户完成从安装、输入命令到听到回复的整套流程，并支持切回中文。

| 环节 | 计划改动 | 是否需要重新训练 |
| --- | --- | --- |
| 界面与使用说明 | 抽取按钮、设置、状态和错误文案，增加语言选择；补齐英文安装与使用指南 | 不需要训练模型，属于界面与文档本地化 |
| 常用操作与 Windows 适配 | 为应用、音量、亮度、设置、时间等规则增加英文表达；处理英文系统控件、应用别名、日期和时间格式 | 优先改规则与系统适配，让英文基础操作也能绕过大模型 |
| 模型理解与回答 | 使用已有英文或双语能力的模型，调整中文限定提示；让英文输入仍输出相同 Skill ID 和合法参数，并按所选语言回答 | 先验证现有模型；提示、规则或模型替换仍无法达到要求时，再评估针对性微调 |
| 英文语音输入 | 引导选择受支持的英文听写语言，核对麦克风、输入语言和识别结果；后续识别引擎另做适配 | 使用现成英文识别能力不要求自训识别模型 |
| 英文朗读与个人音色 | 补充英文声音选择，修正固定中文的引擎参数；检查数字、缩写、分句及中英混读，使用独立英文文本试听 | 先测试现有双语模型和参考音；个人音色的发音或自然度不足时，再决定是否补英文数据、微调或更换模型 |

当前源码中，[规则路由](../desktop/keypilot/assistant_router.py)与[问答提示](../desktop/keypilot/ollama_bridge.py)仍以中文为主；[语音 worker](../desktop/keypilot/voice_worker.py)已有 ZipVoice 中英模型/参考音分流，但 Qwen 路径仍有固定 `Chinese` 参数。这些是需要处理的应用适配点，不能直接归因于基础模型不懂英文。

上游已有可复用能力：[Windows Voice Typing](https://support.microsoft.com/en-us/accessibility/windows/use-voice-typing-to-talk-instead-of-type-on-your-pc)支持英文听写，[ZipVoice](https://github.com/k2-fsa/ZipVoice)和[Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS)也有英文合成能力。因此，**英文版不把重新训练模型作为前置条件**。历史上已做过英文音色 v7 和中英文分流，见[声音迭代记录](VERSION_HISTORY.md)；这些私人资源不随项目公开，也不等于整个 App 已完成英文化。

首轮验收使用英文 Windows 和一组中英文对应任务，例如 `Open Calculator`、`Set the volume to 30 percent`、`Set a timer for five minutes`，分别验证界面反馈、Skill/参数、实际执行、英文朗读及切回中文后的行为。模糊或无法支持的请求应清楚提示；时间、日期、数字和中英混合文本单独检查。先完成基本英文体验，再依据错误类型决定是否投入模型训练。

## 声音方向：一次制作，本地长期使用

声音能力作为[个性化语音子项目](VOICE_PROJECT.md)组织，计划把三条已有适配或实验路径做成清楚的产品选项：较强 GPU 上短样本直接合成，云端辅助制作后 CPU 长期使用，以及直接调用云端 API。

### 本地 GPU 直接合成

显卡与显存满足所选模型要求时，使用本地语音模型和短参考音直接合成，减少对云端制作的依赖。参考音驱动的零样本克隆不一定需要为每位用户训练新权重；它与专门微调一个音色是两种不同流程。当前项目已有相关适配与实验记录，未来需要把兼容硬件检查、模型安装、试听和运行管理统一成 App 内的体验。

短参考音生成、CPU ONNX 推理与量化已有上游基础，可参考 [ZipVoice](https://github.com/k2-fsa/ZipVoice) 和 [sherpa-onnx 部署文档](https://k2-fsa.github.io/sherpa/onnx/tts/zipvoice.html)。这些能力来自相应上游，具体质量仍需对实际模型、录音和设备验证。

### 云端辅助制作，再部署到本地

面向没有足够本地算力、但希望获得定制声音的用户，探索可选的按次制作服务：

1. 用户提供自己的或取得许可的短参考音，完成录音质量和转写检查。
2. 在所选服务允许的用途内，使用云端高质量语音模型生成教师语料；必要时租用云端算力运行训练。
3. 用这些数据微调可部署的本地语音模型，保留独立验证和试听文本；后续如研究蒸馏，单独验证其方法与效果。
4. 选择通过质量检查的候选，导出兼容的本地推理资源，完成量化前后对照和首次合成检查。
5. 导入用户电脑，后续日常合成使用本地资源，不必为每次朗读继续购买云端合成额度。

这里迁移的是通过训练得到的本地模型能力，不能假设能够从云端厂商直接导出其私有模型参数。项目历史已探索过“云端教师语料 → ZipVoice 微调 → ONNX INT8 本机部署”；当前公开版本提供研究代码与过程说明，尚未形成锁定全部依赖、面向普通用户的一键制作服务。现状见 [语音研究工具](VOICE_LAB.md) 和 [语音迭代历史](VERSION_HISTORY.md)。

**作者提出的初步成本目标是约 3 美元/次音色制作。** 这是待实测的目标预算，不是已经核算的完整成本、云厂商报价或最终售价。评估时需固定语料规模和质量要求，分别记录云端合成、训练算力、失败重试、存储与交付成本；如果提供付费服务，定价还需覆盖实际维护与支持。可先验证小规模、可重复的制作流程，再决定收费方式。

质量至少需要验证两点：未参与训练的中英文文本能否清晰、稳定朗读，避免漏字、重复和发音错误；以及相同文本与响度条件下，用户盲听是否更偏好新音色。训练损失下降或导入成功，都不能单独代表声音达到交付标准，扩大教师语料也不保证完整继承教师模型的音质。

公开仓库继续只提供实现方法、规范和空模板，作者的语音包、私人录音和权重不上传。未来云端辅助制作涉及用户选择的参考材料，需在产品中明确处理位置、用途和删除方式，并提供纯本地路径；这项规划不启用或授权上传现有本地资源。

### 直接云端 API：按需选择声音质量与响应

对于愿意持续使用云服务、更重视所选服务首音速度和声音表现的用户，保留直接调用云端 TTS 的路径。项目已有火山引擎流式合成与播放适配，后续需要把服务配置、音色选择、连接状态及费用来源做成普通用户能理解的界面。

这一方案不需要在用户电脑常驻大型语音模型，但日常合成会继续使用服务额度。它是否比本地方案更快、更自然，要由具体模型、网络和文本测试决定。声音子项目可以进一步发展为独立的制作、试听、部署工具，同时为 KeyPilot 和其他应用提供声音能力。

## 长期方向：面向不同品牌与自配电脑

目标用户包括没有满意预装助手的小厂整机用户、自配主机用户，以及希望自行选择模型、声音和服务提供方的人。项目希望把按键、输入、系统操作、问答与声音反馈连成稳定的日常体验，让用户不必因为更换电脑品牌而重新组织整套使用方式。

可以按硬件和需求提供不同组合：

- 基础电脑先使用规则操作、系统声音，以及适合其资源的小型本地模型。
- 有较强 GPU 的电脑选择更大的本地模型和本地语音合成。
- 需要特定能力的用户选择 API 模型，在产品内明确服务来源和费用；是否更快或更准确由任务评测决定。

硬件自动匹配、可替换模型和可移植声音包，应共同服务于低门槛体验。长期竞争力需要来自安装成功率、日常操作可靠性、声音体验、持续成本和维护质量。

### 如何判断这个方向的前景

官方资料表明，个人助手与本地推理已经是多个平台持续投入的方向：

| 已核对事实 | 对 KeyPilot 的启示 |

| 联想于 2025-02-25 公告在指定 AI PC 新品上通过天禧 AS 部署端侧 DeepSeek 模型；2025-07-26 的官方文章列出包括通义千问在内的可选择模型生态。[端侧部署公告](https://brand.lenovo.com.cn/brand/ppn03246.html)、[模型生态说明](https://brand.lenovo.com.cn/brand/ppn03405.html) | 厂商正在投入端云结合与统一入口；产品支持有具体机型与服务范围，不能推成所有联想电脑都具备同样能力 |
| 微软的个人 Copilot 已支持语音和文件操作；Windows Actions 实验预览可执行电脑任务，Edge 和 Copilot Studio 另有网页与企业代理产品。各自的条件见[能力核对](MICROSOFT_COMPARISON.md)。Foundry Local 也提供本地推理与硬件适配。[Windows AI 官方 FAQ](https://learn.microsoft.com/en-us/windows/ai/faq) | AI 正从回答问题延伸到执行任务。KeyPilot 将这一方向聚焦到用户自己的日常电脑：常用动作本机完成，模型和声音可选择，代理任务逐步接入同一个语音入口；可复用成熟运行时加快产品化 |

基于这些资料与当前项目能力，**本项目对前景的判断是：个人电脑助手正在从“提供答案”走向“接受目标并完成任务”，KeyPilot 希望成为普通 Windows 用户可自主配置、低成本持续使用的语音执行入口。** 用户能够保留熟悉的操作方式与个人音色，再按硬件和需求选择模型；厂商也可以在这套基础上提供经过适配的体验。

机会具体落在日常任务完成质量、可选择的能力来源和持续使用成本，而不仅是把安装步骤变少。低门槛安装是让这些价值真正到达用户的必要条件。上述是有官方发展动向支持的产品判断，实际需求强度和商业规模仍需用户验证；不以“小厂和自配电脑无法使用 AI”作为前提。现有独立助手的对比见 [同类方案分析](DIFFERENTIATION.md)。

## 合作与商业化设想

厂商与模型提供方合作已有官方先例：联想于 2025-02-21 披露与 DeepSeek 在个人智能和企业智能领域合作；通义实验室负责人在 2023-12-07 的公开发言中提出与联想探索 AI PC 端云协同，该发言由联想官网于 12-24 发布。前者是明确的合作披露，后者是公开的合作方向表态，不据此推断独家关系或未公布的签约条件。[DeepSeek 合作披露](https://brand.lenovo.com.cn/brand/ppn03235.html)、[通义实验室发言](https://brand.lenovo.com.cn/brand/ppn02465.html)

在个人用户版本稳定后，可以探索与小型整机厂商、装机商或模型提供方合作：由合作方承担适配、模型部署或一定额度的服务成本，KeyPilot 提供统一的助手界面与操作接入。用户获得预先验证的组合，仍保留选择其他模型与声音的入口。

可讨论的合作内容包括预装与售后支持、符合分发许可的本地模型包，以及明确用量范围的 API 额度。厂商提供模型或补贴服务，不自动意味着用户永久免费无限使用；需要事先明确费用承担、更新维护和数据处理责任。正式分发前也需明确本项目与第三方组件、模型的许可，目前仓库尚未指定独立开源许可证，见 [第三方组件与分发范围](../THIRD_PARTY_NOTICES.md)。

以上均为未来设想。KeyPilot 当前没有宣布与文中提及的厂商或模型提供方建立合作。本阶段最有价值的验证，是让目标用户在自己的电脑独立安装并持续使用，再以实际留用情况、问题反馈和运行成本决定合作范围。
